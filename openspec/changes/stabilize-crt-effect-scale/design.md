# Design

## Context

See `proposal.md` — Why. The effect is a single GLSL ES 1.00 pass generated by
`src/features/console/crt/preset.ts`; this build of RetroArch cannot create the
render targets a multi-pass chain needs, so the composite pass is the only
pass. The shader already receives `InputSize`, `TextureSize` and `OutputSize`,
and already normalises the frame varying to frame-relative `uv`:

```glsl
vec2 span = max(InputSize / TextureSize, vec2(0.0001));
vec2 uv = tex_coord / span;
```

What is still expressed in output pixels:

| term | current expression | consequence |
|---|---|---|
| scanline phase | `uv.y * OutputSize.y * 1.5` | `~229 * DPR` lines across the picture |
| scanline jitter | `sin(gl_FragCoord.y * 1.5)` | wobble pitch follows the backbuffer |
| shadow mask | `mod(gl_FragCoord.x, 3.0)` | `480 * DPR` mask periods |
| ghost blur | `4.0 / OutputSize` | blur radius shrinks as DPR rises |
| grain seed | `uv * OutputSize` | grain cell is one output pixel |

`OutputSize` is the real device-pixel backbuffer. The core's Emscripten platform
layer watches the canvas and calls `update_canvas_dimensions(CSS size ×
devicePixelRatio)`, so at DPR 3 `OutputSize.y` is 2880, not the requested 960.
The player documents and `player-crt` promise that display density does not
change the look; this is the gap.

`usePlayerScale` requests a 1440x960 CSS box and lets CSS fit it to the stage.
The design deliberately keeps that layout: the canvas is *not* pinned to
1440x960 physical pixels.

## Goals / Non-Goals

**Goals:**

- The number of scanlines relative to the picture is the same at every DPR,
  window size and fullscreen state, and follows the emulated frame's line
  count.
- Mask, jitter and blur are expressed in frame/source units so their scale is
  stable too.
- A visible, anisotropic beam blur: horizontal radius > vertical radius,
  applied to the base picture and the ghost halo.
- Stay single-pass, use only the uniforms RetroArch already supplies, and keep
  the tuned constants single-sourced and unit-testable.

**Non-Goals:**

- Pinning the drawing buffer to 1440x960 device pixels. That is the alternative
  fix analysed in D4 and deferred.
- Changing chroma offsets, grain, flicker, vignette, tonemap, the toggle, or
  reduced-motion selection.
- A stage-aware effect (e.g. fading the mask when the stage is small); that
  would need a new uniform or preset reload path.

## Decisions

### D1. Scanline pitch follows the source line count

Use `InputSize.y`, not `OutputSize.y`:

```glsl
float lines = max(InputSize.y, 1.0);
float phase = uv.y * lines * 6.2831853;       // one period per source line
float scans = clamp(
  1.0 - SCANLINE_STRENGTH * (0.65 - 0.18 * sin(6.0 * time - phase)),
  0.0, 1.0);
```

- 224 lines for NTSC, 239 for PAL, 448 for hi-res. The roll term stays
  `6.0 * time`, so the roll speed remains about one line per frame.
- At DPR 1 this is 224 lines instead of the reference's ~229 (about 2% coarser,
  imperceptible); the archived `player-crt-shader` design left exactly this as
  an open question.
- `InputSize` is the logical frame size the core produced; `TextureSize` is the
  padded texture, so `InputSize.y` is not inflated by padding.

Alternatives considered:

- **Fixed `960 * 1.5` phase (~229).** Simpler and matches the reference count,
  but stays at 229 for PAL/hi-res and preserves the "the buffer is fixed"
  assumption that the platform layer breaks. Rejected.
- **Hard-coded 224.** Works for the common case but is wrong for 239/448.
  Rejected.

### D2. Mask, jitter and blur use frame units

Add frame constants interpolated from `CRT_OUTPUT`, so the numbers live in one
place:

```glsl
#define FRAME_WIDTH 1440.000
#define FRAME_HEIGHT 960.000
```

- **Mask:** `1.0 - 0.23 * clamp(mod(uv.x * FRAME_WIDTH, 3.0) / 2.0, 0.0, 1.0)`.
  This is 480 periods in the 1440 frame, identical to the current look at
  DPR 1, and no longer 480×DPR.
- **Jitter:** `sin(uv.y * lines * 6.2831853) / FRAME_WIDTH * 0.25`. One wobble
  per source line, with the amplitude expressed in frame pixels.
- **Blur:** offsets are `vec2(BLUR_X / FRAME_WIDTH, BLUR_Y / FRAME_HEIGHT)`
  instead of `GHOST_BLUR / OutputSize`.

Grain stays `uv * OutputSize`: it is per-display noise rather than part of the
picture pattern, and normalising it to the frame would make it disappear on a
small stage. This is called out so the remaining output-space term is a
deliberate choice, not an oversight.

### D3. One 5-tap anisotropic kernel, used twice

Replace `ghostBlur` with `blurX` and `blurY` in frame pixels. Starting table:

| parameter | value | meaning |
|---|---|---|
| `blurX` | 6.0 | horizontal step, frame px |
| `blurY` | 2.5 | vertical step, frame px |
| weights | centre 2, ±X 1 each, ±Y 0.5 each | horizontal stronger in radius and weight |

The kernel stays a 5-tap cross (centre plus four axis taps), normalised by the
weight sum. It is the same shape the ghost halo already uses, so the change is
contained; the horizontal radius is more than twice the vertical one, satisfying
the requested anisotropy. `tex()` linearises each tap before weighting, so the
blur is done in linear light.

Use it for the base colour as well as the ghost halo:

- `col.r/g/b` sample the blurred frame at the existing chroma offsets.
- The three ghost samples keep their existing time-varying offsets but use the
  same blurred frame.

This is a deliberate departure from the reference, where the base uses an
unblurred accumulate buffer and only the ghost reads the blurred one; the
requested look is softer than the reference. If the cross kernel shows
diagonal artefacts on high-contrast detail during tuning, the fallback is a
9-tap 3x3 binomial with the same `blurX`/`blurY` steps; that is a tuning change,
not a spec change.

Cost: the base goes from 3 direct taps to 3 × 5 = 15 taps, while the ghost
stays 15, taking the shader from about 18 to 30 taps per pixel. At 1440x960
that is roughly 2.5 G taps/s at 60 fps; at a DPR 3 backbuffer (4320x2880) it is
roughly 22 G taps/s, which may not hold 60 fps on a phone. Mitigations, in
order: measure on the verification box; reduce the ghost to 3 taps if needed;
or open a follow-up to pin the buffer. The buffer is not pinned in this change.

### D4. Keep the backbuffer at device resolution

The player still requests a 1440x960 CSS box and CSS-fits it to the stage. The
emulator may render that frame at DPR-scaled resolution, and the pattern no
longer cares because every pattern term is frame/source anchored.

Alternative: set the canvas CSS size to `1440 / dpr × 960 / dpr` so the
platform layer reports a 1440x960 device buffer. That makes the spec sentence
literally true and cuts the phone's fill cost by about 9x, but Emscripten's
`setCanvasSize` removes the CSS width/height, so the size has to be re-asserted
after every resize; it also makes large retina stages slightly soft. Rejected
for this change, recorded as the follow-up lever if D3's fill cost becomes a
problem.

### D5. Verification is visual, not just source-level

The unit tests can pin the shader source, but only a rendered frame shows
whether the phone still aliases. The verification plan is:

- `preset.test.ts` pins the anchor (`InputSize.y` present in the scanline
  phase, `uv.y * OutputSize.y` absent), the frame constants, the mask basis,
  and `blurX > blurY`.
- A DPR 2 (or phone-sized) e2e run confirms the game still plays and the CRT
  toggle still works. It does not assert a specific backing size, because the
  platform layer may render at device resolution.
- Golden captures on the verification box at DPR 1, 2 and 3 and at a phone
  viewport: count scanline periods by image analysis, check that the phone no
  longer shows low-frequency bands, and compare horizontal vs vertical edge
  softening. The local container cannot run Chromium (missing `libnss3` /
  `libasound`), so browser verification is remote.

## Risks / Trade-offs

- [Hi-res 448-line frames double the scanline count and can alias on a phone] ->
  physically correct for the signal; keep the source-line anchor, note it in
  the docs, and revisit only if a stage-aware cap becomes possible.
- [The mask is still 480 periods across the picture, which is near the
  Nyquist limit on a small phone stage] -> it is the reference pitch and is
  identical to the DPR 1 look; if captures still show mask moiré, stop and
  propose a mask-pitch change (for example, tying it to the source pixel grid)
  rather than silently changing it here.
- [Blur cost at DPR 3] -> measure; fall back to a 3-tap ghost or open the
  buffer-pinning follow-up. Do not ship a phone frame-rate regression.
- [Blur changes the reference look] -> intentional and documented; the tuned
  tint, gain, tonemap, gamma and scanline strength are untouched, and the
  before/after captures make the change reviewable.
- [`InputSize.y` may be reported differently by another core or mode] -> clamp
  to at least 1; verify PAL and hi-res frames on the verification box. The
  shader is regenerated per launch, so no stored state is affected.
- [Cross-kernel artefacts on fine detail] -> switch to the 9-tap binomial with
  the same steps; the parameter table is the only place to change.

## Migration Plan

No data migration. The shader preset is rebuilt from `buildShaderSource()` at
every launch and written into the emulator filesystem, so there is nothing
stored to migrate. Rollback is the previous release; toggling CRT off still
bypasses the effect and the reduced-motion still variant is unchanged. The new
`blurX`/`blurY` defaults are the tuning surface if the look needs adjustment
after release.

## Open Questions

- The exact `blurX`/`blurY` values and whether the 5-tap cross is smooth
  enough. The specs only require horizontal > vertical and frame units; the
  numbers are settled by verification-box captures, not by a spec decision.
